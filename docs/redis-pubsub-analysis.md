# Redis Pub/Sub 使用分析

## 使用场景

项目使用 Redis Pub/Sub 做**跨实例敏感词热更新通知**——当词条变更时，发布一个 `"rebuild"` 消息通知所有实例重建本地词库。

相关代码：`internal/infrastructure/mq/redis_pubsub.go`

## 当前场景适用性分析

该场景恰好规避了 Redis Pub/Sub 的主要缺陷：

| Redis Pub/Sub 的固有问题 | 本项目是否受影响 |
|---|---|
| 消息不持久化，离线订阅者丢消息 | **影响小** — 实例重启时本身会从 DB 全量加载词库，不依赖历史消息 |
| 没有 ACK 机制，无法保证送达 | **影响小** — 丢一条通知最多导致某实例短暂使用旧词库，不会造成数据不一致 |
| 无消息堆积能力，消费慢就丢 | **影响小** — 消息体极小（仅 `"rebuild"` 字符串），处理也很快 |
| 广播模式，无法做消费组负载均衡 | **没问题** — 这里就是要广播给所有实例 |

## 值得注意的点

### 1. 短时间批量更新导致重复 rebuild

如果批量修改了 100 个词条，会发 100 次 `PublishWordUpdate`，每个实例触发 100 次 rebuild。可以加一个**防抖（debounce）**：

```go
// 收到通知后延迟 500ms 执行，期间如果有新通知则重置计时器
// 这样批量更新只触发一次 rebuild
```

### 2. Redis 断开期间的更新会丢失

项目已经做了断线重连（指数退避，最大 30s），这很好。但重连期间的通知会丢失。可以考虑：

- 重连成功后**无条件触发一次 rebuild**，确保不会错过更新

### 3. 如果未来对可靠性要求提高

当前场景（通知性质、可容忍丢失）用 Pub/Sub 合适。但如果未来需要：

- 消息不能丢 → 考虑 **Redis Streams**（有持久化、消费组、ACK）
- 更高可靠性 → 考虑 **NATS / RabbitMQ / Kafka**

## 结论

当前场景下 Redis Pub/Sub 是合理的选择。它用于"通知"而非"传递关键数据"，丢消息不会导致数据不一致（重启时有全量加载兜底）。主要可优化的点是加个防抖避免重复 rebuild，以及重连后自动补一次 rebuild。
