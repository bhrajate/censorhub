# CensorHub 性能测试报告

- 生成日期：2026-05-13
- 被测版本：commit `984a014`（main 分支最新）
- 测试类型：HTTP REST 接口压测；单实例本地部署；模拟跨网延迟

---

## 1. 测试目标

1. 在新硬件环境下复测 CensorHub 单实例吞吐上限与延迟分布。
2. 量化不同"跨网"延迟档位（同机房/同城/跨区域/跨国）对吞吐的影响。
3. 对比核心接口（`/detect`、`/batch`）与旁路接口（`/replace`、`/highlight`、`/healthz`、`/metrics`）的性能特征。

## 3. 测试方法

### 3.1 压测矩阵

| 维度 | 档位 |
|---|---|
| RTT 延迟 | 0 / 20 / 50 / 150 ms（同机房 / 同城 / 跨区域 / 跨国） |
| 并发连接数 | 50 / 200 / 500 |
| 单组时长 | 30 秒 |
| 核心接口（全矩阵） | `/api/v1/filter/detect`、`/api/v1/filter/batch` |
| 对照接口（仅 0/50ms × c=200） | `/api/v1/filter/replace`、`/highlight`、`/healthz`、`/metrics` |

总计 31 组 × 30s ≈ 16 分钟。

### 3.2 跨网延迟模拟

使用 **toxiproxy** 在 `127.0.0.1:20080` 监听并转发到被测服务 `127.0.0.1:18080`，通过 toxic（latency）在上/下行各注入 `RTT/2` ms，等价往返 RTT。

| 档位 | RTT | 场景 |
|---|---|---|
| 0 ms | 0 ms | 同机房（toxiproxy 原生开销 ≤ 1 ms） |
| 20 ms | 20 ms | 同城机房 / 同一大区 VPC |
| 50 ms | 50 ms | 跨区域（如华东 ↔ 华北） |
| 150 ms | 150 ms | 跨国（亚洲 ↔ 北美） |

> 局限：只模拟了额外 RTT，没有丢包/抖动/带宽限制。真实公网会更差。

### 3.3 测量指标

- `requests`：有效完成的 HTTP 请求数
- `rps`：每秒请求数（wrk "Requests/sec"）
- `latency_avg`：wrk 线程级平均
- `p50 / p75 / p90 / p99 / max`：wrk `--latency` 分布
- `errors`：socket error（connect/read/write/timeout）汇总
- `non2xx`：非 2xx 响应数

## 5. 数据解读

### 5.1 峰值吞吐

- `/detect` 单接口峰值：**25,681 RPS**（RTT=0 / c=200），p50 ≈ 7 ms，p99 ≈ 395 ms
- `/detect` 文本处理吞吐：25,681 × 100 字符（平均） ≈ **2.57 MB/s** 的文本匹配
- `/batch` 文本峰值：**~31,655 条文本/秒**（RTT=0 / c=500，每请求 10 条）
- `/replace` 9,461 RPS，`/highlight` 9,089 RPS
- `/healthz` 18,617 RPS 为框架天花板参考值

### 5.2 RTT 对吞吐的侵蚀

以 `/detect @ c=200` 为例：

| RTT | RPS | 相对 0ms | 理论上限（Little's Law） |
|---|---:|---:|---:|
| 0 ms | 25,681 | 100% | — |
| 20 ms | 7,772 | 30% | c=200 / 20ms = 10,000 |
| 50 ms | 3,530 | 14% | c=200 / 50ms = 4,000 |
| 150 ms | 1,207 | 5% | c=200 / 150ms = 1,333 |

**结论**：低并发下 RTT 是主导因素。150ms 档 c=200 的 1,207 RPS 接近理论上限 1,333 的 91%，说明服务端处理时间极短（~0.4 ms/请求），几乎全部延迟来自网络 RTT。

**提升跨网吞吐的唯一办法是加并发。** c=500 / 150ms 下 RPS 达到 3,145，说明 keep-alive 下连接复用彻底。

### 5.3 并发甜点

`/detect` 在 RTT=0ms 下的吞吐随并发变化：

```
c=50    → 17,933 RPS
c=200   → 25,681 RPS   ← 峰值
c=500   → 13,867 RPS   ← 过载回落
```

**c=200 是 `/detect` 的最优并发**，22 线程 CPU 上 25K+ RPS 是非常优秀的单实例表现。c=500 时吞吐下降 46%，表明连接调度和锁竞争开始显现。

`/batch` 的曲线：

```
c=50    → 2,563 RPS
c=200   → 1,305 RPS   ← 谷底（10 路 fan-out 争抢）
c=500   → 3,166 RPS   ← 回升（排队均匀化）
```

batch 的 U 形曲线仍然存在，但相比之前的数据已经大幅改善。

### 5.4 尾延迟分析

| 场景 | p50 | p99 | max |
|---|---:|---:|---:|
| detect × 0ms × 50 | 2.56 ms | 361.58 ms | 715.84 ms |
| detect × 0ms × 200 | 6.95 ms | 395.33 ms | 737.22 ms |
| detect × 0ms × 500 | 37.45 ms | 536.83 ms | 909.47 ms |
| batch × 0ms × 50 | 20.64 ms | 475.12 ms | 837.97 ms |

- **p50 延迟极低**：detect 在 c=200 下仅 7 ms，说明 AC 匹配 + JSON 序列化的端到端开销非常小
- **p99 在 360-540 ms 区间**：比之前的秒级尾延迟大幅改善，但仍高于生产理想值（<200 ms）
- **p99 与 p50 的比值约 50-60x**：主要由 WSL2 环境的 VirtIO 时间抖动贡献，生产裸机预期可压到 50-100 ms

### 5.5 服务端 CPU 利用

测试期间 22 个逻辑核，wrk 吃 ~2-3 核，server 吃 ~10-12 核。**服务端 CPU 在 c=200 时约 50-60% 利用率**，c=500 时约 75-85%。仍有余量，瓶颈在业务层（中间件链、L1 缓存锁、Redis 往返、JSON 序列化）而非 CPU。

### 8.3 c=5000 的 Socket Errors 分析

c=5000 时全部 12 组均出现 **~897 个 socket errors**，数量高度一致，指向：

1. **系统级 fd 限制**：WSL2 默认 `ulimit -n` 通常为 1024，wrk 5000 连接 + 服务端 5000 连接远超此限制
2. **toxiproxy 连接上限**：toxiproxy 单实例默认有连接数限制
3. **服务端 backlog 队列满**：Go `net.Listen` 默认 backlog 128，高并发下 SYN 队列溢出

> 建议：如需测试 c=5000+，需先调整 `ulimit -n 65535`、增大 `net.core.somaxconn`、以及考虑绕过 toxiproxy 直连。

### 8.4 尾延迟代价

c=5000 时的"高 RPS"是以**尾延迟爆炸**为代价换来的：

| 场景 | RPS | p50 | p99 | max | errors | 体验判定 |
|---|---:|---:|---:|---:|---:|---|
| detect × 0ms × 200 | 25,681 | 6.95 ms | 395 ms | 737 ms | 0 | **最优** |
| detect × 0ms × 1000 | 14,054 | 68 ms | 1.03 s | 2.34 s | 0 | 可接受 |
| detect × 0ms × 2000 | 11,024 | 191 ms | 9.07 s | 12.74 s | 0 | p99 不可接受 |
| detect × 0ms × 5000 | 13,377 | 58 ms | 23.63 s | 29.21 s | 897 | **过载** |
| batch × 0ms × 500 | 3,166 | 105 ms | 980 ms | 1.97 s | 0 | **最优** |
| batch × 0ms × 1000 | 975 | 1.14 s | 1.45 s | 2.00 s | 0 | p50 偏高 |
| batch × 0ms × 2000 | 2,809 | 617 ms | 8.06 s | 10.84 s | 0 | p99 不可接受 |
| batch × 0ms × 5000 | 2,559 | 257 ms | 14.21 s | 17.59 s | 897 | **过载** |

### 8.5 稳定性观察

- c=1000 / c=2000：**全部 errors=0、non2xx=0**，服务稳定
- c=5000：**全部出现 ~897 socket errors**，但 non2xx=0（没有 5xx），说明成功处理的请求都返回了正确结果
- 过载表现为**请求排队 + 尾延迟膨胀 + 部分连接被拒**，而不是服务崩溃——这是正确的降级行为

### 8.6 对生产容量规划的修正

| 规模 | 推荐单实例 conns | 推荐副本数（例：目标 10K RPS） |
|---|---|---|
| 小型 SaaS (<100 RPS) | 50–200 | 1（热备 1 副） |
| 中型公司 (500–2K RPS) | 200–500 | 2 |
| 超大规模 (10K+ RPS) | **200–1000** | **1–2**（单实例 25K RPS 即可覆盖） |

**经验准则**：
1. **单实例 c=200 是最优甜点**：吞吐最高（25K RPS）、尾延迟最低（p99 < 400ms）
2. **c=1000 是可接受上限**：`/detect` 仍可维持 14K RPS 零错误，p99 ~1s
3. **c=2000 尾延迟已不可接受**：p99 6-9 秒，仅适合非实时场景
4. **c=5000 触及系统限制**：出现 socket errors，需调系统参数才能继续压测
5. **`/batch` 应用更低的 max_conns**：batch 10 路 fan-out 意味着实际并发 10×，建议 c≤500
